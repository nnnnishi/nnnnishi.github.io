Beware of Fragmentation: Scheduling GPU-Sharing Workloads with Fragmentation Gradient Descent

断片化に気をつけよ：GPU を共有するワークロードを断片化の勾配降下で配置する

  • Qizhen WengHKUST
  • Lingyun YangHKUST
  • Yinghao YuAlibaba Group・HKUST
  • Wei WangHKUST
  • Xiaochuan TangAlibaba Group
  • Guodong YangAlibaba Group
  • Liping ZhangAlibaba Group

1 枚の GPU を複数の機械学習タスクで分け合うと、各 GPU に中途半端な空きが残り、合計では空いているのに次のタスクを置けない GPU が増える。Weng らは次に来るタスクの大きさの分布に対して、どれだけの空きが使えなくなるかの期待値を断片化と定義し、配置のたびにその増加が最小になるノードと GPU を選ぶ FGD を提案した。Alibaba の実データでは割り当てられない GPU を既存の詰め込み型の方式より最大 49% 減らした。

  • 割り当てられない GPU を最大 49% 削減約 1.2k ノード・6.2k GPU のクラスタを実データで再現した実験で、既存の方式より 33〜49% 少なく、GPU 150〜290 枚分を余分に割り当てられた（論文 §6.2）。
  • 断片化 = 次のタスクに使えない空きの期待値ノードの断片化を、タスクの種類 \(m\) の出現割合 \(p_m\) で重み付けた \(F_n(M)=\sum_m p_m F_n(m)\) で測る。「どのタスクも置けない空き」だけを数える絶対的な定義は、ほぼ役に立たない。
  • 配置ごとに断片化の増分が最小の場所へ候補のノードと GPU に仮に置いて増分 \(\Delta\) を計算し、最小の場所を選ぶ。断片化を減らす向きに一歩ずつ進むので「勾配降下」と呼ぶ。
背景

GPU を分け合うと割当率は上がるが、細切れの空きが残って大きなタスクが置けなくなる

大企業のクラスタでは GPU の利用率が 25% から 50% 未満にとどまると報告されている。対策として、1 枚の GPU を複数のタスクに分ける GPU 共有が広まった。論文は Alibaba の本番クラスタ H（約 1.2k ノード、6.2k を超える GPU、107k CPU コア）を調べた。約 7.6k のタスクを配置した時点で GPU の割当率は 92% だったが、約 500 枚の GPU が割り当てられずに残った。約 92% のノードでは空きが GPU 1 枚未満で、待っているタスクの 49% は GPU 1 枚以上を求めていた。

多次元のビンパッキング（箱詰め）にもとづく既存の方式（最も空きが少ないところに置く Best-fit、ベクトルの向きをそろえる Dot-product など）は、この状況にうまく合わない。論文は理由を 2 つ挙げる。1 つのタスクは 1 枚の GPU の中で連続した容量を使い、0.3 枚と 0.7 枚に分けて置けない。また、複数の GPU を持つノードは、1 枚の大きな GPU とも、GPU ごとに独立した次元とも見なせない。

問題設定

断片化を「次に来るタスクに対して使えなくなる空き」の期待値として定義する

ノード \(n\) の GPU \(g\) の空きを \(R_{n,g}\)（0 から 1）、CPU の空きを \(R^{\mathrm{CPU}}_n\) とする。タスク \(m\) は CPU \(D^{\mathrm{CPU}}_m\) と GPU \(D^{\mathrm{GPU}}_m\)（1 未満なら共有、1 以上なら整数枚）を求める。GPU の空きはまるごと空いている GPU の枚数に、一部だけ空いている GPU の最大の空きを足した 1 つの数 \(R^{\mathrm{GPU}}_n = \sum_g \lfloor R_{n,g}\rfloor + \max_g (R_{n,g} - \lfloor R_{n,g}\rfloor)\) で表す。

あるタスク \(m\) から見たノード \(n\) の断片化 \(F_n(m)\) は、次の 3 つの場合に分けて決める。

  • タスクがノードに入らない（CPU か GPU が足りない）：空いている GPU はすべて断片とみなす。\(F_n(m)=\sum_g R_{n,g}\)（式 2）。
  • 入り、GPU を使う：要求より小さい空きしかない GPU だけが断片になる。\(F_n(m)=\sum_g R_{n,g}\,\mathbb{1}\big(R_{n,g} < \min\{D^{\mathrm{GPU}}_m, 1\}\big)\)（式 3）。1 枚以上を求めるタスクから見ると、一部だけ空いた GPU はすべて断片である。
  • GPU を使わないタスク：そのタスクは GPU を使えないので、空いている GPU はすべて断片とみなす。

そのうえで、クラスタに来るタスクの種類 \(m\) とその出現割合 \(p_m\)（目標のワークロード \(M\)）で平均をとる（式 1）。

\[ F_n(M) = \sum_{m \in M} p_m\, F_n(m), \qquad \sum_m p_m = 1, \qquad f_N(M) = \frac{\sum_n F_n(M)}{\sum_n \sum_g R_{n,g}} \]

\(f_N(M)\) はクラスタ全体の断片化率である（式 5、6）。論文は比較として「ワークロードのどのタスクも入らない空き」だけを断片とする絶対的な定義も調べた。この定義は全体の 0.06% しかない小さなタスク（平均で CPU 3.2、GPU 0.07）だけで決まり、実験の間ずっと 5% 未満のままで、配置の判断に使える信号にならなかった。

手法

候補ごとにタスクを仮に置き、断片化の増分が最も小さいノードと GPU を選ぶ

タスクを置くたびに空きは減り、断片化は増えやすい。Fragmentation Gradient Descent（FGD）は、その増加が最も小さい向きを選ぶ（論文 Algorithm 1）。

  • 1. 絞り込み：資源が足りないノードや、GPU の型などの制約を満たさないノードを除く。
  • 2. 仮の配置：残った各ノードにタスクを仮に置く。GPU を共有するタスクなら、ノード内のすべての GPU を試す。
  • 3. 増分の計算：仮に置いた後の断片化を \(F^{-}_n(M)\) として \(\Delta = F^{-}_n(M) - F_n(M)\) を求める。\(\Delta\) は負にもなりうる。
  • 4. 決定：\(\Delta\) が最小のノードと GPU にタスクを置く。

論文の例では、空きが 0.5 と 1.0 の GPU を持つノードに、0.3・0.5・0.7 枚を求めるタスクが同じ割合で来る。この例を CPU を無視して解説者が計算すると、置く前のノードの断片化は 0.7 のタスクから見た 0.5 だけなので \(F = 0.5/3 \approx 0.17\) である。0.3 のタスクを空き 1.0 の GPU に置くと空きは 0.5 と 0.7 になり、\(F\) は 0.17 のまま（\(\Delta=0\)）。空き 0.5 の GPU に置くと空きは 0.2 と 1.0 になり、0.2 がどのタスクにも使えないので \(F=0.2\)（\(\Delta \approx +0.03\)）。FGD は前者を選ぶ。次の 0.5 のタスクを空き 0.5 の GPU に置くと断片化は 0 になり、最後の 0.7 のタスクも入る（以上、解説者の計算）。

タスクの種類の数は少ない（7.6k のタスクで約 80 種類）ので、増分の計算は軽い。1.2k ノードで 1 回の判断は数百ミリ秒で、各ノードのスコアは並列に計算できる。実装は Kubernetes v1.25.0 のスケジューラのプラグイン（Go で 1 万行以上）である。

実験の結果

実データを再現したクラスタで、割り当てられない GPU を 33〜49% 減らし、条件を変えても常に最良だった

Alibaba が公開したクラスタ H のトレースから、約 1.2k ノード・6.2k GPU のクラスタを再現した。タスクは GPU を使わないもの 13.3%、GPU を共有するもの 37.8%、1 枚 48.0%、2 枚・4 枚・8 枚がそれぞれ 0.2%・0.2%・0.5% である（論文 Table 1）。タスクを復元抽出で次々に到着させ、要求の合計が GPU の総容量に達した時点の「割り当てられなかった GPU の割合」を 10 回の平均で比べた。比較相手は Random、Best-fit、Dot-product、GPU Packing（使用中の GPU から先に詰める）、GPU Clustering（同じ大きさの要求をまとめる）である。

予約枠の断片化と予約受付の研究の中での位置づけ

「将来の需要の分布で重み付けた、使えない空きの期待値」を断片化の指標にし、それを貪欲に抑える方式である

  • 断片化の定義：空きの細かさそのものではなく、来そうな要求に対して使えない空きの量を、要求の出現割合で平均する。どの要求も入らない空きだけを数える定義は信号が弱いことを、実データで示した点が重要である。
  • 美容室の予約への使い方：GPU の空き容量を「スタイリストの連続した空き時間の長さ」、タスクの大きさの分布を「施術時間の分布」に置き換えると、予約を入れたときに増える「どの施術にも足りない空き時間」の期待値を最小にする枠を選ぶ、という指標がそのまま作れる。違いは、GPU は時間ではなく容量の次元で、空きの位置（時刻）や営業時間の端の扱いがないこと、来る要求の分布を既知としていることである。
  • 限界：評価は次の 1 タスクだけを見る 1 歩先の指標で、何手も先を読むものではない。資源が十分にある初期には最適とは限らず、増分が出ないときは Best-fit に切り替えることを提案している。実機ではなく、実データを使った忠実度の高いエミュレーションでの評価である。
  • 関連：時間方向の空きの断片化を扱う研究には、病院の予約表を詰め直す Lian ら（2010）、予約の空きを区間として管理するグリッド計算の Castillo ら（2008）、社用車の利用の断片化を評価する Koetter ら（2015）がある。
